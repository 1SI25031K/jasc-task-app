# JASC79 タスク・NA管理アプリ 要件定義書 v1.3

最終更新：2026-11-03
- v1.2：Slack 通知・英語 UI・進捗グラフ・議事メモからの NA 生成を追加
- v1.3：負荷の見える化（自動負荷・体感負荷・余力マップ）、依頼と承諾の流れ、個人 DM リマインド、週次の完了まとめを追加

対象：第79回日米学生会議 日本側実行委員会

---

## 1. 目的と解決したい課題

| 課題 | このアプリでの解決策 |
|---|---|
| 誰がどんな作業をしているか見えず、**任せて良いか判断できない** | タスクと NA を役職ごとに表示する／**自動負荷と体感負荷**を全員が見られる「余力マップ」／担当者を選ぶときに負荷を表示する |
| 見えないことで、**不要な不満**が生まれる | **依頼と承諾の流れ**（勝手に振らない）／毎週の「先週の完了」まとめで貢献を見えるようにする |
| **リマインドの手間** | Slack の**個人 DM で自動リマインド**（期限前日・当日・超過・停滞・依頼の未返答・体感負荷の入力） |
| 定例会で決まったことが放置される | 議事メモから NA 候補を作り、その場で登録する |

あわせて、来年度の実行委員にも引き継げる、シンプルで壊れにくい仕組みにする。

| 項目 | 内容 |

| 利用者 | 日本側実行委員（約8名）。米国側実行委員の参加時は英語 UI で利用 |

| 画面言語 | 日本語／英語（ユーザーごとに切替。既定は日本語） |

| AI（議事メモ → NA） | Gemini API（Google AI Studio で API キーを発行、`google-genai` SDK）。モデル名は設定で指定 |
| ホスティング | Streamlit Community Cloud（無料） |
| ソース管理 | GitHub（**private リポジトリ**） |

| テスト | `pytest` |
| 開発環境 | macOS + Google Antigravity |

### 設計方針
- **データアクセス層を抽象化する**（`Repository` インターフェース）。実装は「インメモリ（テスト・ローカル開発用）」と「Google スプレッドシート」。
- **外部サービスも抽象化する**（`Notifier` / `NaExtractor`）。テストではダミー実装を使い、実際に通信しない。
- 画面（pages）にはビジネスロジックを書かない。期限判定・負荷計算・リマインド対象の抽出・通知文の組み立て・AI 出力の検証は `core/` に置き、テストする。
- 画面の文言は翻訳ファイル（`locales/ja.toml` / `locales/en.toml`）から読む。フェーズ2の画面作成時点からこの仕組みで作る。
- 曜日・時刻・しきい値などの運用パラメータは `settings` シートに置き、コードを変えずに調整できるようにする。
- アプリが止まっても、実行委員がスプレッドシートを直接見て運用を継続できるデータ構造にする。

## 4. データ設計（スプレッドシートのシート構成）

### 4.1 `members`（メンバー）
| 列 | 型 | 説明 |
|---|---|---|
| member_id | 文字列 | 例：`m001` |
| display_name | 文字列 | 表示名（姓のみ等） |
| display_name_en | 文字列 | 英語表示名。空なら display_name を使う |
| email | 文字列 | ログイン照合用。小文字で比較する |
| main_roles | 文字列 | 主役職の role_id をカンマ区切り |
| lang | 文字列 | `ja` / `en` |
| slack_user_id | 文字列 | **DM の送り先**（例：`U0123ABCD`）。空の人には DM を送らず、管理者向けの一覧に「未設定」と出す |
| reminders_enabled | TRUE/FALSE | 個人 DM リマインドを受け取るか（既定：TRUE） |
| is_admin | TRUE/FALSE | 管理者フラグ |
| active | TRUE/FALSE | FALSE の人はログイン不可・通知対象外 |

### 4.2 `roles`（役職）
| 列 | 型 | 説明 |
|---|---|---|
| role_id | 文字列 | 例：`r_selection` |
| name / name_en | 文字列 | 表示名（日本語／英語） |
| category | 文字列 | `主役職` / `副役職` / `サイト` / `その他` |
| sort_order | 数値 | 表示順 |
| active | TRUE/FALSE | FALSE は非表示 |

初期データ（暫定。管理者が随時追加・変更する）：

- **主役職**：実行委員長、副実行委員長、財務、広報、選考
- **副役職**：春合宿、安全保障研修、自主研修、直前合宿、リスクマネジメント、JASC COMEBACK、業務効率化、定例会、報告書、関西業務、報告会、福島研修
- **サイト**：東京サイト、関西サイト、岩手サイト
- **その他**：CVC（※正式名称・区分は要確認）

※「関西業務」（副役職）と「関西サイト」（サイト）は別の役職。
※英語名の初期値はエージェントが案を作り、管理者が確認する。
※担当者の割り当ては実在の氏名を含むため、リポジトリには書かず、管理者がスプレッドシートに直接登録する。

### 4.3 `role_assignments`（役職の担当割り当て）

### 4.5 `checkins`（体感負荷）
| 列 | 説明 |
|---|---|
| checkin_id | 自動採番 |
| member_id | 回答した人 |
| date | 回答日（Asia/Tokyo） |
| score | 体感負荷 1〜10（1＝かなり余裕がある、10＝限界） |
| comment | 任意の一言（例：「来週テスト」「岩手の調整が山場」）。最大100文字 |
| auto_load_at_checkin | 回答時点の自動負荷（後から振り返るため） |

- 同じ人が同じ日に2回答えた場合は、新しい回答で上書きする。
- 入力欄に「**体調などの詳しい理由は書かなくて大丈夫です**（全員が閲覧できます）」と表示する。

| 列 | 説明 |
|---|---|
| timestamp | 日時（Asia/Tokyo） |
| member_id | 操作した人（定時処理は `system`） |
| task_id | 対象タスク |
| action | `create` / `create_from_minutes` / `update` / `request` / `accept` / `consult` / `archive` / `restore` |
| field / old_value / new_value | 変更内容（update 時） |

### 4.7 `meetings`（議事メモから NA を生成した会議）
| 列 | 説明 |
|---|---|
| meeting_id / meeting_date / title | 会議の情報 |
| created_by / created_at | 実行した人・日時 |
| generated_count / saved_count | AI が出した候補数／実際に登録した数 |

※議事メモの本文は保存しない。

### 4.8 `daily_snapshots`（進捗グラフ用の日次集計）
| 列 | 説明 |
|---|---|
| date | 集計日 |
| scope_type | `ALL` / `role` / `member` |
| scope_id | role_id または member_id（ALL のときは空） |
| total / done / open / overdue | タスク総数／完了数／未完了数／期限切れ NA 数（アーカイブ除く） |
| completion_rate | done / total |
| auto_load | 自動負荷（scope_type=member のとき） |

- 同じ日付・同じ対象の行がすでにあれば上書きし、重複させない。

### 4.9 `reminder_log`（送信済みリマインド）
| 列 | 説明 |
|---|---|
| sent_at | 送信日時 |
| member_id | 送り先 |
| kind | `due_tomorrow` / `due_today` / `overdue` / `overdue_escalation` / `waiting` / `stale` / `request_pending` / `checkin` / `high_load_alert` |
| task_id | 対象タスク（checkin・high_load_alert は空） |
| date_key | 送信日（YYYY-MM-DD） |

- **同じ（member_id, kind, task_id, date_key）の組み合わせは1日1回しか送らない**。定時処理を再実行しても二重送信しないため。

### 4.10 `settings`（運用パラメータ）
| key | 初期値 | 説明 |
|---|---|---|

| daily_job_time | `08:00` | 定時処理の時刻（参考値。実際の時刻は GitHub Actions の cron で決まる） |
| load_window_days | `14` | 自動負荷の計算に含める期間（日） |
| weight_points | `軽=1,中=2,重=3` | 重さのポイント |
| overdue_escalation_days | `3` | 超過何日で役職責任者にも知らせるか |
| stale_days | `7` | 停滞とみなす日数 |
| request_reminder_days | `2` | 依頼に返事がないとき何日後にリマインドするか |
| high_load_score | `8` | 体感負荷アラートのしきい値 |
| high_load_consecutive | `2` | しきい値以上が何回続いたらアラートを出すか |
| summary_channel_id | （空） | 毎朝のまとめ・週次まとめを投稿するチャンネル |
| app_url | （空） | 通知に載せるアプリの URL |

### 5.3 依頼と承諾の流れ
- 自分を担当者にしてタスクを作成した場合：`assignment_status=承諾済`、`requested_by` は空。
- **自分以外**を担当者にした場合：`assignment_status=依頼中`、`requested_by=作成者`。担当者に DM「○○さんから依頼が届いています」を送る（次の定時処理で）。
- 担当者が「承諾」→ `承諾済`。依頼した人に DM で知らせる。
- 担当者が「相談したい」（コメント必須）→ `相談中`。依頼した人に、コメント付きで DM で知らせる。依頼した人は、担当者を変更する（再び依頼になる）か、内容を調整して再依頼する。
- 依頼中のまま `request_reminder_days` 日が過ぎたら、担当者にリマインドする。
- 依頼中・相談中のタスクも、担当者の自動負荷には含める（「来るかもしれない仕事」も負荷として見える方がよいため）。ただし余力マップでは、承諾済の分と依頼中の分を色分けして表示する。

### 5.4 負荷の計算ルール
- **重さの目安**（入力欄の横に表示する）：
  - `軽`＝1〜2時間で終わる（例：メール1通、日程調整）
  - `中`＝半日〜1日程度（例：資料作成、見積の比較）
  - `重`＝数日以上かかる、または複数人との調整が必要（例：宿泊先の確保、プログラムの設計）
- **自動負荷（pt）**＝ 担当者が自分で、status ≠ 完了、アーカイブされていない、かつ「NA 期限が今日から `load_window_days` 日以内」または「期限切れ」のタスクについて、重さのポイントを合計したもの。
- **体感負荷**＝最新の checkins の score。最後の回答から7日以上経っていたら「未回答」と表示する。
- **ずれの判定**：全メンバーの自動負荷を 1〜10 に換算し（メンバー内の最大値を10とする）、体感負荷との差が4以上なら印を付ける。換算方法は余力マップの「？」マークに説明として表示する。
- **体感負荷アラート**：体感負荷が `high_load_score` 以上の回答が `high_load_consecutive` 回続いたら、実行委員長・副実行委員長（`role_assignments` から取得）に DM で知らせる。本人には「無理せず相談してください」という一文と、余力マップへのリンクを送る。

### 5.5 期限・停滞の判定ルール
- **期限切れ NA**：status ≠ 完了 かつ na_due < 今日（Asia/Tokyo）
- **今週期限**：status ≠ 完了 かつ 今日 ≤ na_due ≤ 今日+7日
- **停滞タスク**：status ≠ 完了 かつ updated_at が `stale_days` 日以上前
- **完了率**：完了件数 ／ アーカイブを除く全件数。0件なら「—」
- 日付・時刻はすべて Asia/Tokyo で扱う。

### 5.6 個人 DM リマインドのルール（F18）
毎朝の定時処理で、次の条件に当てはまる人に DM を送る。**1人あたり1日1通にまとめる**（項目ごとにメッセージを分けない）。

| 種類 | 条件 | 送り先 |
|---|---|---|
| 明日期限 | na_due = 明日 | 担当者 |
| 今日期限 | na_due = 今日 | 担当者 |
| 期限切れ | na_due < 今日（毎朝） | 担当者 |
| 期限切れ（責任者へ） | 超過が `overdue_escalation_days` 日以上 | そのタスクの各役職の責任者（担当者本人を除く）。1タスクにつき、責任者へは**最初の1回のみ** |
| 待ちの相手 | status=待ち かつ waiting_on_member_id がある（2日に1回） | 待たれている人 |
| 停滞 | 停滞タスク（週1回、月曜） | 担当者 |
| 依頼の返事待ち | 依頼中が `request_reminder_days` 日以上 | 担当者 |
| 新しい依頼・依頼への返事 | 前回の定時処理以降に発生 | 担当者／依頼した人 |
| 体感負荷の入力 | `checkin_weekdays` の曜日で、その日まだ回答していない | 全員 |
| 体感負荷アラート | 5.4 の条件 | 委員長・副委員長、本人 |

- DM の文面は、その人の `lang` に合わせる（日本語／英語）。
- 各項目にアプリの該当ページへのリンクを付ける。
- 送信内容は `reminder_log` に記録し、同じ内容を1日に2回送らない。
- `reminders_enabled=FALSE` の人には、体感負荷アラート以外の DM を送らない。
- `slack_user_id` が空の人は送信をスキップし、毎朝のまとめ投稿の末尾に「Slack ID 未設定：○名」とだけ出す（管理者が気づけるように）。

### 5.7 F14（議事メモ → NA）の詳細仕様
- Gemini に渡すもの：議事メモ本文（マスキング後）、会議日、役職一覧（role_id・名前）、メンバー一覧（member_id・表示名のみ。メールアドレスは渡さない）。
- 送信前に、メールアドレス・電話番号らしき文字列を `[メール]` `[電話番号]` に置き換える。画面にも「個人情報は貼り付けないでください」と表示する。
- 構造化出力（JSON スキーマ指定）で、候補ごとに `title` / `next_action` / `owner_member_id` / `role_ids` / `na_due` / `weight` / `evidence`（根拠となるメモの短い引用）を返させる。不明な項目は空。
- 返ってきた値は必ず検証する：存在しない ID は空にする、不正な日付は空にする、文字数の上限を超えたら切り詰める。
- 担当者・期限が空の候補は、画面で入力しないと登録できない。
- 1回に送れる議事メモは2万文字まで。
- API エラー時は「時間をおいて再試行してください」と表示し、入力したメモは画面に残す。

### 6.1 セキュリティ（**リリース条件**）
| # | 要件 |
|---|---|
| S1 | 認証必須。未ログイン・未登録ユーザーにはデータを一切表示しない（データ読み込み前に認証チェックで `st.stop()`） |
| S2 | 秘密情報（OIDC クライアントシークレット、`cookie_secret`、サービスアカウント鍵、Slack Bot トークン、Gemini API キー）は `.streamlit/secrets.toml`・Community Cloud の Secrets・GitHub Actions の Secrets にのみ置く。Git にコミットしない |

| S5 | スプレッドシートへの書き込みは `value_input_option="RAW"`（数式インジェクション対策）。AI 生成の文字列も同様 |

### 6.2 パフォーマンス・可用性
- Google Sheets の読み込みは `st.cache_data`（TTL 60秒程度）でキャッシュし、書き込み後はキャッシュを破棄する。
- Community Cloud は約12時間アクセスがないとスリープする。リマインド・まとめ投稿・集計は GitHub Actions で動くため、アプリがスリープしていても止まらない。
- 定時処理は毎朝1回・数分程度とし、GitHub Actions の無料枠（private リポジトリで月2,000分）に収める。
- 定時処理が失敗したら、GitHub のメール通知で管理者が気づけるようにする。途中で失敗して再実行しても、`reminder_log` と `daily_snapshots` の重複防止で二重送信・二重集計にならないこと。
- スプレッドシートのバージョン履歴をバックアップとして使う。加えて月1回、管理者がシートを複製して保管する。

### 6.3 UI/UX
- 日本語／英語。PC とスマートフォンの両方で使える（スマホでは1列表示）。
- ステータスの色：未着手＝グレー、進行中＝青、待ち＝黄、完了＝緑。期限切れは赤。
- 主要操作（NA の更新、体感負荷の回答、依頼の承諾）は **2クリック以内**。
- 体感負荷の色：1〜4＝緑、5〜7＝黄、8〜10＝赤。色だけに頼らず数値も表示する。
- 負荷に関する画面では、責める表現（「遅れ」「少ない」など）を避け、中立的な表現（「期限を過ぎた NA」「余裕がある」など）を使う。
- エラー時は、何をすればよいかを表示する。

### 6.4 保守性・引き継ぎ
- `README.md` にセットアップ・デプロイ・シート構成・定時処理・各 API キーの管理方法・`settings` の各項目の意味を記載する。
- 主要な関数には日本語の docstring を付ける。
- `core/` のロジックは `pytest` でテストする。外部サービスはダミー実装でテストする。

## 7. 運用ルール（アプリの外で決めること）

- **体感負荷は評価に使わない。** 分担を話し合うための材料として使う。アプリ導入時に実行委員会で合意する。
- 体感負荷は週3回（月・水・金）に回答する。状況が大きく変わったら、曜日に関係なくいつでも更新してよい。
- 定例会の冒頭で、F5（期限アラート）と F15（余力マップ）を画面共有して確認する。
- タスクを他の人に振るときは、アプリで「依頼」する。口頭で頼んだ場合も、後でアプリに登録する。
